## Breaking News

**OpenAI shipped a new model pair: GPT-6.2 Astra and GPT-6.2 Sol.** Astra is the new frontier model; Sol is the efficient, everyday-work model. Both are available in the API as `gpt-6.2-astra` and `gpt-6.2-sol` ([OpenAI announcement](https://openai.com/index/introducing-gpt-6-2-astra-sol/), [Simon Willison summary](https://simonwillison.net/2026/Nov/17/gpt62-astra-and-sol/)). The key pitch is work-per-token: OpenAI says both models deliver better results on demanding tasks with fewer output tokens, which means more within usage limits and lower cost at scale ([official model video](https://www.youtube.com/watch?v=C1zYX5jwqq4)). Astra is aimed at complex professional artifacts — slides, spreadsheets, documents — while Sol is positioned as the efficient workhorse for everyday work. A Codex demo even shows Astra reconstructing a room from two video frames and turning it into an interactive Blender set ([demo video](https://www.youtube.com/watch?v=tKoDPOrLMX0)). This is an API/frontier-model story, not an open-weight release, but the cost-per-output-token angle matters for anyone building agent pipelines.

Practical ways to use it:

- Start an eval on `gpt-6.2-sol` for your high-volume summarisation, classification, and agent sub-calls. If quality holds, it should be cheaper per completed task.
- Reserve `gpt-6.2-astra` for the hardest document/spreadsheet generation and complex agentic work — that is its stated target.
- Upgrade your local tooling; Simon Willison shipped LLM 0.38 with support for the new model names ([source](https://simonwillison.net/2026/Nov/17/gpt62-astra-and-sol/)).

## Work Watch — Snowflake, dbt & Cortex Code

### Snowflake

**Spark Monitoring UI reached General Availability.** Snowflake’s release notes say it is for monitoring and troubleshooting Snowpark Connect for Spark batch jobs and sessions directly in Snowsight ([release note](https://docs.snowflake.com/en/release-notes/2026/other/2026-11-18-spark-monitoring-ui-ga), [new-features index](https://docs.snowflake.com/en/release-notes/new-features)). If you run Spark workloads against Snowflake, this is the first place to look when jobs stall.

**Cortex AI Function Optimization went GA on Nov 16.** It automatically searches across prompts and models, compares quality against estimated cost, and recommends more cost-efficient AI function implementations ([release note](https://docs.snowflake.com/en/release-notes/2026/other/2026-11-16-ai-function-optimization-ga)). That is a direct lever for tuning Snowflake Cortex spend rather than doing the prompt/model search by hand.

Two practical Snowflake + AI-agent posts also landed on the official channel: an **agent factory** experiment that migrated PostgreSQL views and functions to Snowflake with parallel AI translators, scripted checks, and an independent AI reviewer ([Snowflake blog](https://medium.com/snowflake/building-an-agent-factory-for-data-migrations-a-small-test-with-snowflake-9d4622c8f2c7?source=rss----34b6daafc07---4)); and a **Claude Code + Snowflake research environment** where SQL and an MCP server give agents access to versioned data in Snowflake ([Snowflake blog](https://medium.com/snowflake/ai-research-environment-with-claude-code-and-snowflake-74f8a8a99fcb?source=rss----34b6daafc07---4)). Both are good templates if you are building code-gen agents on Snowflake.

### dbt

**dbt’s November 2026 update is release-grade.** dbt v2 is now GA across major warehouses; local unit tests are in alpha; batch testing can cut runtime and warehouse queries materially; there is a free dbt State plan; Wizard Desktop is in public beta; and dbt Charts now work in Claude and ChatGPT ([dbt blog](https://www.getdbt.com/blog/whats-new-in-dbt-november-2026)). For modelling and testing workflows, the local unit tests and batch-testing improvements are worth trialling this week.

## Headlines

- **Open-source Trainium inference engine appears.** TrnRT, an inference engine for AWS Trainium, is open-sourced and currently serves GLM-5.3 Flash (FP8) on a trn2.48xlarge, with two instances per box behind a cache-aware router and 3.57M TPM on SemiAnalysis’s AgentX benchmark ([GitHub](https://github.com/RunanywhereAI/trnrt)). This is a signal that cheap open-weight serving on custom AWS silicon is becoming a practical option.
- **Simon Willison explores external sandboxes for coding agents.** He worked with Prime Radiant on safer ways to sandbox code executed by agents, specifically to reduce the damage a mistake or prompt injection could cause when running local models ([post](https://simonwillison.net/2026/Nov/17/external-sandboxes-for-coding-agents/)). If you run local LLMs in agentic loops, this is the threat model to study.
- **llama.cpp news for the local/quantization crowd.** A November recap points to llama.cpp v1.0.0 with FP8 KV-cache support, CUDA OCP FP8 support, and additional model support including Kimi-K3.1 ([recap](https://localmodelwatch.tsuchitsuchi.com/en/2026/11/17/llamacpp-v100-released/)); v0.9.0 brought OCP FP8 E4M3 quantization support ([recap](https://localmodelwatch.tsuchitsuchi.com/en/2026/11/17/llama-cpp-v0-9-0-released/)). FP8 is the trend to track for faster local inference with lower VRAM.
- **“Not Everything Needs an LLM.”** PostHog’s decision-model essay argues that deterministic decision models often beat LLMs at a fraction of the cost — a useful lens when designing pipelines that should route around model calls ([article](https://newsletter.posthog.com/p/decision-models), [HN discussion](https://news.ycombinator.com/item?id=50535740)).
- **Datasette Lite was rewritten around service workers + Pyodide.** Simon Willison’s browser-based Datasette now runs almost indistinguishably from the server-side app, using a carefully crafted URL against `lite.datasette.io` ([post](https://simonwillison.net/2026/Nov/17/datasette-lite/)). It is a nice reference architecture for in-browser data tooling.
