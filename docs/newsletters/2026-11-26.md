## Work Watch — Snowflake, dbt & Cortex Code

### Snowflake

**Cortex AI Function Optimization reached GA.** Snowflake's release notes say you can now automatically search across prompts and models to improve custom AI function implementations, compare quality and estimated cost, and identify lower-cost model options that still meet workload requirements ([1](https://docs.snowflake.com/en/release-notes/2026/other/2026-11-16-ai-function-optimization-ga)). For Cortex-heavy accounts, this is a “cost optimisation button” that should go straight into the monthly FinOps review.

**Cortex AI Gateway also hit GA** for inference, observability, and cost management, adding production-facing spend reporting and operational visibility around Gateway usage ([9](https://docs.snowflake.com/en/release-notes/2026/other/2026-11-03-cortex-ai-gateway-ga)). If you route model calls from multiple teams through one gateway, this is the control surface that makes charging back or throttling actually feasible.

**AI_COMPLETE now supports Snowflake Decision in public preview** — a high-throughput classification/scoring model “priced for large-scale decisioning workloads” ([13](https://docs.snowflake.com/en/release-notes/2026/other/2026-11-20-ai-complete-snowflake-decision-public-preview)). Worth evaluating if you are currently burning premium LLM tokens on repetitive classification tasks. The price/accuracy trade-off is the interesting question here.

Two good long-form Snowflake reads landed today. The first is a practical post-mortem on getting an **SPCS Native App onto the Snowflake Marketplace** without copying account metadata out of the consumer’s account: the app reads `ACCOUNT_USAGE`, finds waste and governance gaps, and uses Cortex for insights, all inside the consumer’s own Snowflake account ([Medium](https://medium.com/snowflake/lessons-from-getting-an-spcs-native-app-onto-the-snowflake-marketplace-6b1d1426d70c?source=rss----34b6daafc07---4)). That is a useful reference architecture if you are considering Marketplace-native tools rather than yet another external SaaS connector.

The second is a compelling “entirely in SQL” walkthrough: **scanned homeowner tax records → governed AI agent**, with claims of 100% field accuracy on digital documents, 94% on scans, and a Cortex Agent on top, all without data leaving Snowflake ([Medium](https://medium.com/snowflake/from-scanned-homeowner-tax-records-to-a-governed-ai-agent-entirely-in-sql-8aa4b8fee8f0?source=rss----34b6daafc07---4)). The “no data egress” property is the part that should interest anyone running regulated or public-sector workloads.

Finally, Snowflake Developers published a 60-second explainer on **real-time analytics for AI agents** firing thousands of queries per second. The useful framing: real-time is not just fast queries — it is a balance between query latency, data freshness, and concurrency, and you should consciously choose streaming vs. near-real-time vs. batch ingestion ([Snowflake Developers](https://www.youtube.com/watch?v=xnmB_K2d8l8)).

## Worth a Skim

### Cheaper AI Models Can Make Your Agent Cost More

[Watch on YouTube](https://www.youtube.com/watch?v=LVWD7qYNf-A) · Cloud Codes · 10 min

- A decision model like TypeSafe’s Jev is marketed as up to 100x faster and far cheaper for routine multiple-choice turns, but a model with 92.2% tool-choice accuracy completed only 69.5% of whole agent tasks in the cited paper.
- The failure mode is cascade: one wrong tool choice early in an episode poisons the rest of the run.
- Lesson: evaluate agents end-to-end, not on isolated tool-choice benchmarks. Cheaper turns can still mean more failed episodes — and higher total cost.

### You Probably Don’t Need Kubernetes, Kafka or Redis

[Watch on YouTube](https://www.youtube.com/watch?v=VKy-Qpyh_EQ) · Cloud Codes · 2 min

- 37signals reports that HEY runs 20 million background jobs a day straight through a database table.
- Kafka, Redis, and Kubernetes solve specific scaling symptoms — they are not default starting infrastructure.
- Decision heuristic: start with a load balancer, Docker, and Postgres, and add the heavy tools only when the symptom actually appears.
